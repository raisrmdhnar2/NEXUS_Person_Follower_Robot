# General Concept — NEXUS Following Robot

## 1. Project Overview

This project is a mobile robot inspired by **Karen from SpongeBob SquarePants**.

The robot is named **NEXUS** and is developed as part of the **Technology and Information Department of Brawijaya University**.

NEXUS is designed to:

1. Detect people using a camera.
2. Detect when a person is within the configured interaction range.
3. Recognize a predefined hand gesture as a password.
4. Use the valid gesture to activate the robot.
5. Identify and lock the person who provided the valid gesture as the target.
6. Follow only the locked target.
7. Maintain a predefined distance from the target.
8. Keep the target near the center of the camera view.
9. Provide basic voice interaction and greetings.
10. Allow the locked target to deactivate the robot using the same valid gesture.
11. Automatically deactivate if the locked target is lost for too long.
12. Display different visual states on the robot's monitor.
13. Provide speech responses according to the current robot state.

The robot uses a **Raspberry Pi** for high-level perception, decision making, HMI, and speech control, and an **ESP32** for low-level motor control.

---

# 2. Mechanical Configuration

NEXUS uses a **three-wheel mobile robot configuration** consisting of:

* One passive front caster/free wheel.
* One motorized rear-left wheel.
* One motorized rear-right wheel.

The two rear wheels form a **differential-drive system**.

```text
                    FRONT
                      ↑

                 ┌─────────┐
                 │  FRONT  │
                 │ CASTER  │
                 │  FREE   │
                 │  WHEEL  │
                 └────┬────┘
                      │
              ┌───────┴───────┐
              │               │
              │    NEXUS      │
              │     BODY      │
              │               │
              └───────────────┘
                │           │
                ▼           ▼
          REAR LEFT      REAR RIGHT
            WHEEL          WHEEL
          + MOTOR         + MOTOR
```

### Wheel Roles

| Wheel        | Position     | Type         | Function           |
| ------------ | ------------ | ------------ | ------------------ |
| Front caster | Front-center | Passive/free | Mechanical support |
| Left rear    | Rear-left    | Motorized    | Differential drive |
| Right rear   | Rear-right   | Motorized    | Differential drive |

The front caster has no motor and no encoder. It passively swivels and follows the movement generated by the two rear drive wheels.

# 4. Computing Platform Responsibilities

## 4.1 Raspberry Pi

The Raspberry Pi handles high-level processing.

Responsibilities:

* Camera capture.
* Person detection.
* Person tracking.
* Person proximity detection.
* Hand gesture recognition.
* Gesture-to-person association.
* Password authentication.
* Target selection.
* Target ID management.
* Target tracking.
* Distance sensor processing.
* Follow control.
* Differential-drive velocity calculation.
* UART communication with ESP32.
* Robot state management.
* Monitor/HMI management.
* Speech generation and playback.
* Speech event management.
* Greeting trigger management.
* Speech cooldown management.

The Raspberry Pi does **not** directly generate PWM for the motors.

---

## 4.2 ESP32

The ESP32 handles low-level motor control.

Responsibilities:

* Receive wheel velocity commands from Raspberry Pi.
* Parse UART commands.
* Read wheel encoders.
* Run PID controllers.
* Generate PWM.
* Control the motor driver.
* Control the two rear motors.
* Implement communication timeout.
* Stop the motors when communication is lost.

The ESP32 does **not** perform:

* Person detection.
* Person tracking.
* Gesture recognition.
* Target selection.
* Speech generation.
* HMI management.
* High-level robot state decisions.

# 5. Robot Operating States

The robot uses a state machine.

```text
                         Person Detected
                         Within Range
                              │
                              ▼
                         GREETING
                              │
                              ▼
                            OFF
                              │
                        Valid Gesture
                              │
                              ▼
                      ┌───────────────┐
                      │ TARGET LOCK   │
                      └───────┬───────┘
                              │
                              ▼
                       ┌─────────────┐
                       │   FOLLOW    │
                       └──────┬──────┘
                              │
                 ┌────────────┼────────────┐
                 │            │            │
           Target Lost    Valid Gesture    │
           Too Long       from Target      │
                 │            │            │

                 │            │            │
```

Main logical states:

* `OFF`
* `GREETING`
* `TARGET_LOCK`
* `FOLLOW`
* `DEACTIVATING`

`GREETING` is a short interaction state/event. It does not activate the robot.

# 7. Person Proximity Detection

The greeting should only be triggered when a person is considered **near NEXUS**.

The proximity condition can be determined using:

* Camera-based person detection.
* Bounding-box size.
* Distance sensor.
* Or a combination of camera and distance sensor.

The preferred implementation is to use the **distance sensor as the primary proximity measurement** when reliable target/person distance information is available.

Conceptually:

```text
Camera
  │
  ▼
Person Detected
  │
  ▼
Distance Measurement
  │
  ▼
Is Person Within Greeting Range?
  │
 ┌┴───────────┐
NO            YES
 │             │
 │             ▼
 │          GREETING
 │             │
 └─────────────┘
```

The greeting range should be configurable:

```text
GREETING_DISTANCE = configurable
```

The exact value should be determined experimentally based on the physical robot and environment.

# 8. NEXUS Startup Greeting

When NEXUS detects a person within the configured greeting range, it says:

> **“Welcome to the Technology and Information Department of Brawijaya University! Hello! I’m NEXUS. I’m ready to follow you. Please show me the password.”**

This greeting is **not played immediately after boot**.

The sequence is:

```text
System Initialization
        ↓
OFF
        ↓
Person detected
        ↓
Person within greeting range
        ↓
GREETING
        ↓
Play startup greeting
        ↓
OFF
        ↓
Wait for password
```

The greeting informs the nearby person that:

* NEXUS is active and ready.
* NEXUS can follow them.
* A password gesture is required to activate following.

# 9. Greeting Cooldown

NEXUS must not repeatedly play the startup greeting while the same person remains within the greeting range.

Example:

```text
Person enters range
       ↓
Greeting
       ↓
Person remains nearby
       ↓
NO repeated greeting
       ↓
Person leaves range
       ↓
Greeting system resets
       ↓
Another person enters range
       ↓
Greeting allowed again
```

A configurable cooldown may also be implemented.

Example:

```text
GREETING_COOLDOWN = configurable
```

The exact cooldown should be determined during testing.

The greeting system should therefore maintain a simple interaction condition:

```text
person_near
greeting_already_played
```

When the robot is OFF:

* Motors are stopped.
* No target is locked.
* The monitor displays the live camera feed.
* The robot continuously searches for people.
* If a person enters the greeting range, NEXUS gives the startup greeting.
* NEXUS continuously searches for the valid password gesture.
* A valid gesture can activate the robot.

```text
OFF
 │
 ├── Motors = STOP
 ├── Target ID = NONE
 ├── Monitor = LIVE CAMERA
 ├── Detect nearby person
 ├── Greeting if required
 └── Wait for valid gesture
```

# 11. Password Gesture

NEXUS uses a predefined hand gesture as its password.

The gesture serves as a **toggle command**, but its interpretation depends on the robot state.

### Robot OFF

```text
Valid Gesture
      │
      ▼
Find person associated
with the gesture
      │
      ▼
Lock that person
      │
      ▼
Activate robot
```

### Robot ACTIVE

The same gesture can deactivate the robot, but only when it comes from the currently locked target.

```text
Target performs
valid gesture
      │
      ▼
Verify gesture belongs
to locked target
      │
      ▼
Deactivate robot
```

A valid gesture from another person must **not** deactivate the robot.

# 12. Gesture-to-Person Association

The robot must associate the detected gesture with a person.

For example:

```text
Person 1 ────── ID 1
Person 2 ────── ID 2
Person 3 ────── ID 3
```

If Person 2 performs the valid gesture:

```text
Valid Gesture
      │
      ▼
Gesture detected near Person 2
      │
      ▼
Candidate Target = ID 2
      │
      ▼
Target ID = 2
```

The gesture should not simply be treated as a global command.

The system must determine **which tracked person performed the gesture**.

---

# 13. Target Lock

After a valid activation gesture is detected, NEXUS locks the corresponding person.

Example:

```text
Person 1 → ID 1
Person 2 → ID 2  ← Valid gesture
Person 3 → ID 3

Target ID = 2
```

Once the target is locked:

```text
Target ID = 2
```

NEXUS follows ID 2 even if:

* Another person is closer.
* Another person walks into the camera view.
* Another person performs the same gesture.

The target ID remains associated with the selected person through the tracking system.

A multi-object tracking algorithm is used to maintain identity between frames.

Possible implementation:

* YOLO for person detection.
* ByteTrack or BoT-SORT for tracking.
* OpenCV for image processing.
* MediaPipe or another hand-tracking system for gesture recognition.

Conceptually:

```text
Camera Frame
     │
     ▼

     │
     ▼
Multi-Object Tracker
     │
     ├── Person ID 1
     ├── Person ID 2
     └── Person ID 3
```

If:

```text

```

the controller searches for tracked person ID 2.

# 15. Target Center

NEXUS uses the target's bounding box to determine its horizontal position.

For a target bounding box:

```text
(x1, y1) ──────────────┐
   │                   │
   │      TARGET       │
   │                   │
   └───────────── (x2,y2)
```

The target center is:

$$
x_c = \frac{x_1+x_2}{2}
$$

$$
y_c = \frac{y_1+y_2}{2}
$$

For an image width \(W\):

$$
x_{camera} = \frac{W}{2}
$$

Horizontal tracking error:

$$
e_x = x_c-x_{camera}
$$

Interpretation:

```text
e_x < 0     Target is LEFT
e_x ≈ 0     Target is CENTER
e_x > 0     Target is RIGHT
```

This error is used to calculate the robot's angular velocity.

---

# 16. Distance Measurement

A distance sensor is used to estimate the distance between NEXUS and the target.

The controller uses:

$$
e_d = D_{person}-D_{target}
$$

where:

* \(D_{person}\) = measured target distance.
* \(D_{target}\) = desired following distance.

Behavior:

```text
D_person > D_target
        ↓
Move forward

D_person ≈ D_target
        ↓
Stop / move slowly

D_person < D_target
        ↓
Stop
```

For the first implementation, NEXUS should avoid automatically reversing toward the target when the target is too close.

---

# 17. Follow Controller

The follow controller receives:

* Target horizontal error \(e_x\).
* Target distance \(D_{person}\).

It generates:

$$
V
$$

and

$$
\omega
$$

where:

* \(V\) = linear velocity.
* \(\omega\) = angular velocity.

Conceptually:

```text
Target Center Error ──→ Angular Controller ──→ ω

Target Distance ──────→ Distance Controller ─→ V
```

Then:

```text
                V
                │
                ▼
        Differential Drive
                ▲
                │
                ω
```

---

# 18. Differential Drive

NEXUS uses its two rear motorized wheels for differential drive.

Let:

* \(V_L\) = left rear wheel velocity.
* \(V_R\) = right rear wheel velocity.
* \(W\) = distance between the two rear wheels.
* \(V\) = robot linear velocity.
* \(\omega\) = robot angular velocity.

The wheel velocities are:

$$
V_L = V-\frac{\omega W}{2}
$$

$$
V_R = V+\frac{\omega W}{2}
$$

Therefore:

```text
                  V, ω
                   │
                   ▼
          Differential Drive
                   │
          ┌────────┴────────┐
          ▼                 ▼
       V_left            V_right
          │                 │
          ▼                 ▼
     Rear Left           Rear Right
       Motor               Motor
```

The front caster is passive and does not receive a velocity command.

# 19. Robot Movement

## Move Forward

Both rear motors move forward at approximately the same velocity.

```text
Left  = +
Right = +
```

The caster follows the robot.

---

## Move Backward

Both rear motors move backward.

```text
Left  = -
Right = -
```

---

## Turn Left

The left wheel slows relative to the right wheel.

```text
Left  = slower
Right = faster
```

---

## Turn Right

The right wheel slows relative to the left wheel.

```text
Left  = faster
Right = slower
```

---

## Rotate in Place

If required, the rear wheels can rotate in opposite directions:

```text
Left  = +
Right = -
```

or:

```text
Left  = -
Right = +
```

The caster swivels during the rotation.

# 21. ESP32 Motor Control

The ESP32 receives:

```text
V_left
V_right
```

and controls the two rear motors independently.

### Left Motor

```text
Command
   ↓
Left PID
   ↓
PWM
   ↓
Motor Driver
   ↓
Left Rear Motor
   ↓
Encoder
   └──────→ Feedback
```

### Right Motor

```text
Command
   ↓
Right PID
   ↓
PWM
   ↓
Motor Driver
   ↓
Right Rear Motor
   ↓
Encoder
   └──────→ Feedback
```

Each rear motor should have encoder feedback so the ESP32 can regulate actual wheel speed.

# 22. Communication Safety

The ESP32 should implement a communication timeout.

If the Raspberry Pi stops sending commands:

```text
No UART command
      │
      ▼
Timeout detected
      │
      ▼
V_left = 0
V_right = 0
      │
      ▼
STOP ALL MOTORS
```

This prevents the robot from continuing to move if the Raspberry Pi crashes or communication is interrupted.

---

# 23. Target Loss Behavior

Target loss must be handled explicitly.

When the locked target disappears from the tracker:

```text
Target ID not detected
        │
        ▼
Start loss timer
        │
        ├── Target returns
        │       ↓
        │   Continue FOLLOW
        │
        └── Timeout exceeded
                ↓
           DEACTIVATE
```

A practical initial timeout is approximately **1–2 seconds**, which should be calibrated during testing.

---

# 24. Automatic Deactivation After Target Loss

If the target remains lost beyond the configured timeout:

```text
Target Lost
    │
    ▼
Loss Timeout
    │
    ▼
Automatic Deactivation
    │
    ├── Stop motors
    ├── Clear Target ID
    ├── Robot State = OFF
    └── Monitor = LIVE CAMERA
```

NEXUS must **not** automatically search for and reacquire the previous target after the timeout.

A new activation requires the valid password gesture again.

### Target-Loss Speech

When the target is temporarily lost:

> **“Where are you?”**

If the target remains lost until the timeout:

> **“I can’t find you.”**

Each speech event should be triggered once per loss event.

# 26. NEXUS Speech System

NEXUS has a basic speech system that provides contextual voice responses.

Speech is controlled by **robot states and system events** rather than being continuously generated.

The speech system should:

* Play predefined voice lines.
* Trigger speech based on specific events.
* Avoid repeating the same message unnecessarily.
* Use cooldowns where appropriate.
* Prioritize safety and state transitions over speech.
* Allow speech playback to be interrupted if necessary.

# 28. Speech Behavior by State

## Person Detected Nearby

When NEXUS is in `OFF` and detects a person within the configured greeting range:

> **“Welcome to the Technology and Information Department of Brawijaya University! Hello! I’m NEXUS. I’m ready to follow you. Please show me the password.”**

This is the primary **welcome interaction**.

The greeting should not repeat continuously while the person remains nearby.

---

## Activation

After a valid password gesture:

> **“Hello! Nice to see you.”**

After successful target locking:

> **“I’ll follow you.”**

Then NEXUS enters `FOLLOW`.

---

## Following

During normal following, NEXUS may occasionally say:

> **“I’m right behind you.”**

This should not be played continuously.

A cooldown should be implemented between repeated normal-following speech events.

---

## Temporary Target Loss

When the locked target is temporarily lost:

> **“Where are you?”**

If the target returns before the timeout:

```text
Target returns
     ↓
Continue FOLLOW
```

NEXUS does not need to repeat the target-lock speech.

---

## Target Loss Timeout

If the target remains lost beyond the configured timeout:

> **“I can’t find you.”**

Then:

```text

 ↓
Target ID cleared
 ↓
OFF
 ↓
Live Camera
```

---

## Deactivation

When the locked target gives the valid password gesture:

> **“Okay! See you later!”**

Then NEXUS stops the motors and returns to `OFF`.

---

## System Error

If a critical software or hardware error occurs:

> **“Something went wrong.”**

The system should prioritize stopping the robot safely.

# 37. Safety Rules

The following rules are mandatory:

### Rule 1 — No target, no following

The robot must not drive autonomously without a valid locked target.

### Rule 2 — Greeting does not activate the robot

Detecting a nearby person only triggers the greeting.

It does **not** activate following.

A valid password gesture is still required.

### Rule 3 — Target loss timeout

Temporary tracking loss is tolerated for a short configurable period.

Permanent loss causes automatic deactivation.

### Rule 4 — No automatic reacquisition

After target-loss timeout, the robot must not automatically search for the previous target.

Authentication is required again.

### Rule 5 — Only the target can deactivate

A valid password gesture from another person cannot deactivate the robot.

### Rule 6 — Communication timeout

If Raspberry Pi → ESP32 communication fails, the ESP32 must stop the motors.

### Rule 7 — OFF means motors stopped

Whenever the robot enters `OFF`:

```text
V_left = 0
V_right = 0
```

and a stop command must be sent to the ESP32.

### Rule 8 — Speech must not override safety

Speech playback must never prevent or delay a safety-critical motor stop.

For example:

```text
Target Loss Timeout
        │
        ├── STOP MOTORS immediately
        │
        └── Play "I can't find you."
```

Motor safety has higher priority than speech.

### Rule 9 — Greeting must not repeat continuously

NEXUS should not repeatedly greet a person who remains within the greeting range.

The greeting system must use an interaction flag, cooldown, or range-exit reset.

# 40. Final System Definition

The final NEXUS concept is:

> **A three-wheel mobile robot with two independently motorized rear wheels and one passive front caster, using differential-drive locomotion, camera-based person detection and tracking, proximity-based greeting, gesture-based authentication, target locking, distance-aware following, state-based HMI, and contextual voice interaction.**

The control architecture is:

> **Raspberry Pi → Perception → Proximity Detection → Greeting → Authentication → Target Lock → Target Tracking → Follow Controller → Differential Drive → UART → ESP32 → PID → Two Rear Motors**

The mechanical architecture is:

> **1 passive front caster + 2 independently driven rear wheels**

The HMI architecture is:

> **Robot State / Events → HMI Manager → Monitor Display + Speech Manager → Voice Output**

The safety architecture is:

> **Target lost beyond timeout → Motor Stop → Automatic Deactivation → Target Cleared → Live Camera → Re-authentication**

The interaction architecture is:

> **Person Approaches → NEXUS Greets → Password Gesture → Target Lock → Follow → Target Interaction → Deactivation**
